# 长白山北景区天池 · 逐日开放台账

把「今天天池开不开」变成一条可核查的时间序列：逐日抓取「长白山发布」（澎湃号·政务，pphId 111214）的《今日长白山》公报正文，按规则判定北景区天池状态，渲染成一张三年逐日日历。

**在线页面**：https://kenneth-g6.github.io/tianchi-calendar/

**仓库**：https://github.com/Kenneth-G6/tianchi-calendar

**自动更新**：GitHub Actions 每天 UTC 10:00（北京时间 18:00）运行，结果自动提交并发布。

---

## 它统计的是什么

| 状态 | 含义 | 是否可游 |
|---|---|---|
| OPEN | 公报明示「天池正常开放」 | 是 |
| OPEN_DELAY | 明示「X 点开始检票 / 延缓开放」 | 是 |
| PARTIAL | 明示「X 点停止检票」，部分时段可游 | 是（部分） |
| CLOSED_TIANCHI | 天池景点全天关闭 / 暂停游览 | 否 |
| CLOSED_AREA | 北景区整体全天关闭 / 停运 | 否 |
| VEHICLE_STOP | 仅天池车辆停运，景点未明示关闭 | 否（实际不可达） |
| UNCERTAIN | 「是否开放视清雪进度确定」 | 否 |
| NO_RECORD | 当日无任何公开口径 | 不计入分母 |

口径为**游客可达**：北坡上主峰只能乘景区车，车停运即到不了天池观景台，因此 `VEHICLE_STOP` 计入不可游，但在页面中单列一类、不与「景点关闭」混算。

## 关键结论

- 窗口 2023-11-09 起共 1,096 天；
- **可直接逐日核对的只有 2026 年段的 298 天**（253 天有公报），可游率 **48.2%**；
- 2026-01-15 之前，澎湃政务号存档被服务端限制（累计 1,184 篇即 `hasNext=false`），历史段只用单篇公报与媒体公告做点状锚定，**不给开放率**。

## 为什么不给三年的开放率

分母不可知时算出的比率是伪精度。更关键的是**来源偏差**：媒体只转载关闭公告（「天池关闭」是新闻，「正常开放」不是新闻），用媒体记录补历史会系统性高估关闭率。页面的「对抗性验证」章节逐条记录了这些问题，包括一次把 48.2% 误算成 24.2% 的口径事故。

## 仓库结构

```
index.html                 生成的日历（Pages 直接展示此文件）
scripts/build.py           抓取 → 解析 → 统计 → 渲染（唯一入口）
scripts/template.html      页面模板，{{...}} 为注入占位符
data/dailies.json          公报正文缓存（增量抓取用，勿手改）
data/anchors.json          历史单篇核查缓存
.github/workflows/daily-update.yml   每日定时任务
```

## 自动化

- 触发：每天 **UTC 10:00**（北京时间 18:00），外加手动 `workflow_dispatch`；
- 流程：增量抓新公报 → 重新统计 → 覆盖 `index.html` → 提交回仓库 → 部署 Pages；
- 容错：接口不通时保留缓存继续渲染，CI 不失败，页面维持上一版数据；
- 手动全量重抓：Actions 页面点 *Run workflow*，`full_refresh` 填 `true`（解析规则改动后用）。

> GitHub 的定时任务有排队延迟，实际执行通常在北京时间 18:00–18:20 之间；且 `schedule` 只在默认分支上生效。

## 本地运行

```bash
pip install requests
python scripts/build.py     # 产出 index.html
```

## 数据使用边界

- 只对 2026 年成立，单年样本，不能代表年度规律；
- 公报在山门开放前（约 6:20–8:30）发布，反映**早间初始口径**，午后恶化的二次公告不进入日报；
- 「景点开放」≠「能看到天池」，云雾遮挡不记录；
- 灰色格子是信息真空，不代表当日开放或关闭。
