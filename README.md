# 长白山天池 · 逐日开放台账（北 / 西 / 南 三景区）

把「今天天池开不开」变成一条可核查的时间序列：逐日抓取「长白山发布」（澎湃号·政务，pphId 111214）的《今日长白山》公报正文，按体例切成北、西、南三段分别判定，渲染成可切换的三套逐日日历。

**在线页面**：https://kenneth-g6.github.io/tianchi-calendar/

**仓库**：https://github.com/Kenneth-G6/tianchi-calendar

**自动更新**：GitHub Actions 每天三轮（CST 18:00 / 08:30 / 次日 00:00），结果自动提交并发布。

---

## 它统计的是什么

| 状态 | 含义 | 是否可游 |
|---|---|---|
| OPEN | 公报明示「天池正常开放」 | 是 |
| OPEN_DELAY | 明示「X 点开始检票 / 延缓开放」 | 是 |
| PARTIAL | 明示「X 点停止检票」，部分时段可游 | 是（部分） |
| CLOSED_TIANCHI | 天池景点全天关闭 / 暂停游览 | 否 |
| CLOSED_AREA | 北景区整体全天关闭 / 停运 | 否 |
| VEHICLE_STOP | 仅天池车辆停运，景点未明示关闭 | 否（实际不可达） |
| CLOSED_REPAIR | 抢修 / 山体滑坡等临时关闭（南坡常见） | 否 |
| CLOSED_SEASON | 季节性闭园（南坡每年 5 月中—10 月开放，其余时间即此状态） | 否 |
| UNCERTAIN | 「是否开放视清雪进度确定」 | 否 |
| NO_RECORD | 当日无任何公开口径 | 不计入分母 |

### 三坡分别播报

同一篇《今日长白山》里，北、西、南三段是**分别播报**的，同一天三坡结论可能完全不同：

- **北景区**逐日播报，主体是天池 + 瀑布、温泉、小天池、绿渊潭、谷底森林；
- **西景区**逐日播报，天池在海拔高处单独停游，锦江大峡谷通常照常开；
- **南景区**每年 5 月中开山、10 月中闭园，冬季公报只是例行一句「自 10 月 16 日起实施季节性闭园」。

统计口径统一为「**当天能否到达天池**」——坡内其他景点是否开放不计入。因此
「北坡天池车辆停运」记为不可达，即使瀑布、绿渊潭照常开放。三坡日均分开统计，
页面上方三张卡片切换，各自带当年可游率。

口径为**游客可达**：北坡上主峰只能乘景区车，车停运即到不了天池观景台，因此 `VEHICLE_STOP` 计入不可游，但在页面中单列一类、不与「景点关闭」混算。

## 关键结论

- 窗口 2023-11-09 起共 1,096 天；
- **可直接逐日核对的只有 2026 年段的 298 天**（253 天有公报），可游率 **48.2%**；
- 2026-01-15 之前，澎湃政务号存档被服务端限制（累计 1,184 篇即 `hasNext=false`），历史段只用单篇公报与媒体公告做点状锚定，**不给开放率**。

## 为什么不给三年的开放率

分母不可知时算出的比率是伪精度。更关键的是**来源偏差**：媒体只转载关闭公告（「天池关闭」是新闻，「正常开放」不是新闻），用媒体记录补历史会系统性高估关闭率。页面的「对抗性验证」章节逐条记录了这些问题，包括一次把 48.2% 误算成 24.2% 的口径事故。

## 自动化

- 触发：每天三轮 —— **UTC 10:00**（CST 18:00，主更新）、**UTC 00:30**（CST 08:30，晨间票务信号）、**UTC 16:00**（CST 次日 00:00，补漏轮），外加手动 `workflow_dispatch`；
- 第三轮的意义：澎湃列表存在**整日批量延迟入库**（当天发布的稿件次日才可见，已多次实测），晚轮落在索引可见之后，能把前一天的缺口补上；
- **默认是增量模式**：只扫最近 14 天的列表（约 2 页 / 100 条），发现新公报才抓正文，其余全部走缓存；
  追加进台账后重新渲染、提交。漏跑几天也能自动补回——回看窗口覆盖两周。
- 对比：全量模式每天要把 1,184 篇列表翻到底（24 次请求）才能确认「新增了一篇」；增量只要 2 次。
- 容错：接口不通时保留缓存继续渲染，CI 不失败，页脚会标明「官方接口未响应，沿用缓存数据」；
- 手动全量回扫：Actions 页面点 *Run workflow*，`full_refresh` 填 `true`（仅在解析规则变更或缓存损坏时用）。

### 多源交叉验证

官方逐日播报只在「长白山发布」澎湃号，且**并非每天都有**（历史最大断档 5 天）。为在公报缺失时仍有独立证据，
构建脚本额外抓取**票务平台侧写**：去哪儿网长白山北景区页里「含天池主峰车票」的 SKU 的可订日期。

- 判据逻辑：主峰停运当天官方会停止售票并开放退票，所以「某日主峰车票可订」= 官方系统仍在该日售票 → **预期开放**；
- 边界：票务只反映"仍在售卖"，**不等于当日实际开放**——主峰仍可能因瞬时大风临时停运；
- 因此票务信号**只作为交叉验证与预期提示**，日历格子的正式状态仍以官方公报为准，无公报一律留灰、不插值；
- 每天 08:30 那一轮的价值：此时当日票尚未停售，能抓到「今天主峰票是否在售」，这是判断当天开放最接近的独立信号。

`data/last-run.json` 记录了每次运行的 `mode`、`scanned_articles`、`list_api_ok`、
`new_details_fetched`、`play_rate_pct`，以及票务信号 `qunar_ok`、`qunar_today_bookable`、
`qunar_tomorrow_bookable`、`qunar_bookable_dates`；逐次明细留在 `data/crosscheck.json`（保留最近 60 次）。

> GitHub 的定时任务有排队延迟，实际执行通常在北京时间 18:00–18:20 之间；且 `schedule` 只在默认分支上生效。

## 数据使用边界

- 只对 2026 年成立，单年样本，不能代表年度规律；
- 公报在山门开放前（约 6:20–8:30）发布，反映**早间初始口径**，午后恶化的二次公告不进入日报；
- 「景点开放」≠「能看到天池」，云雾遮挡不记录；
- 灰色格子是信息真空，不代表当日开放或关闭。
